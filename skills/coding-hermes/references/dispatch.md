對當次的 plan/工單 md（$ARGUMENTS 有給路徑就用它；沒給就用本 session 最新的 plan 檔）執行派工前客製化檢查。逐條核對，缺什麼就直接補進該 md，不是只回報缺。

## 檢查清單

1. **前情提要（context）**：外部 agent 是全新 session，沒有本對話的任何記憶。工單開頭必須有自足的背景段：系統是什麼、為什麼要做這件事、相關檔案的完整絕對路徑、既有約束（環境、依賴、不可動的部分）。凡是「本對話才知道」的前提，全部寫明。
2. **驗收標準**：明確、可驗證的完成條件清單。含指令的條目要寫出實際指令與預期輸出，讓執行者能自行跑並貼結果（宣告 ≠ 生效）。最好收成**一條以 exit code 判成敗的驗收指令**，主 session 才能機械判定。
3. **只含必要資訊**：刪掉與任務無關的討論史、廢案、內部術語。無關內容會讓外部 agent 偏移。若某資訊不影響執行結果，砍掉。
4. **步驟詳細避免做錯**：每步寫清楚做什麼、在哪個檔案/路徑、預期結果為何。有歧義的地方（命名、位置、格式）直接指定，不留給執行者猜。危險或不可逆操作要標明界線（哪些不能碰）。
5. **範圍界定**：明確寫出「不做什麼」（out of scope），防止執行者自行擴張。
6. **可執行性**：逐條掃過工單的每個步驟，確認全部可由 agent 用 Bash / HTTP API / 檔案寫入自動完成。出現「WebUI」「Settings →」「請使用者手動/貼上/點選」等字樣一律改寫成 API 或 CLI 路徑。若目標設備無終端、無 GUI，真的無法自動化的步驟（例：需要真人發第一則訊息才能建立綁定）必須標為 optional，並提供自動化的替代驗證方式。

## 完成後

- 逐條回報檢查結果（通過/已補）。
- 呈報工單 md 的**完整絕對路徑**，由使用者自行轉貼給執行者（不自行派送、不代跑）。
